## 1. Project Overview

This assignment demonstrates two operating system synchronization problems using semaphores and monitors:

1. Readers-Writers Problem using Semaphores
2. Readers-Writers Problem using Monitors
3. Dining Philosophers Problem using Semaphores
4. Dining Philosophers Problem using Monitors

The project records execution events, validates synchronization behaviour, generates HTML simulations, and opens the generated simulation in a web browser.

## 2. Project Structure

- `common/sync_trace.py` — Records state changes, validates execution traces, generates HTML simulations, and opens the output in a browser.
- `readers_writers/semaphore/rw_semaphore.py` — Readers-Writers implementation using semaphores.
- `readers_writers/monitor/rw_monitor.py` — Readers-Writers implementation using locks and condition variables.
- `dining_philosophers/semaphore/dp_semaphore.py` — Dining Philosophers implementation using semaphores.
- `dining_philosophers/monitor/dp_monitor.py` — Dining Philosophers implementation using locks and condition variables.
- `generated_html/` — Stores the HTML simulation generated by each program run.
- `ai_prompts/prompts.md` — Contains the AI tools used, prompts, and details of my own contributions.

## 3. How to Run the Programs

The programs can be executed directly using Python 3.8 or later. No compilation step is required.

Open the project folder in VS Code, open the terminal, and execute the following commands from the project root directory.

### Program 1: Readers-Writers using Semaphores

```bash
python readers_writers/semaphore/rw_semaphore.py --readers 4 --writers 2 --rounds 3
```

### Program 2: Readers-Writers using Monitors

```bash
python readers_writers/monitor/rw_monitor.py --readers 4 --writers 2 --rounds 3
```

### Program 3: Dining Philosophers using Semaphores

```bash
python dining_philosophers/semaphore/dp_semaphore.py --meals 3
```

### Program 4: Dining Philosophers using Monitors

```bash
python dining_philosophers/monitor/dp_monitor.py --meals 3
```

## 5. Output and Simulation

When a program runs, it prints the execution trace in the terminal, checks the recorded events, and generates an HTML simulation in the `generated_html/` directory.

The HTML file can be opened in a web browser. The simulation provides the following controls:

- **Start:** Starts the simulation.
- **Step:** Advances through the recorded events.
- **Reset:** Resets the simulation.
- **Speed:** Adjusts the playback speed.
- **Timeline:** Allows inspection of execution events.

Automatic browser opening can be disabled by setting `OS_NO_OPEN=1`, if supported by the environment.

## 6. Validation

The program checks the recorded execution trace against synchronization requirements.

### Readers-Writers Problem

- Multiple readers may read simultaneously when no writer is writing.
- A writer must have exclusive access to the shared resource.
- Reading and writing must not overlap.

### Dining Philosophers Problem

- A philosopher must acquire both required forks before eating.
- A fork cannot be shared by two philosophers simultaneously.
- The synchronization mechanism should prevent deadlock under the tested execution conditions.

The validation output should be checked after each execution. A successful test does not, by itself, prove that starvation is impossible under every possible scheduling condition.

## 7. Known Limitations

1. **Monitor implementation:** Python does not provide a native monitor keyword. The monitor implementations use locks and condition variables.
2. **Semaphore fairness:** Python semaphores do not guarantee strict FIFO ordering, so fairness is not formally guaranteed.
3. **Possible starvation:** Depending on the implementation and thread scheduling, a reader, writer, or philosopher may experience indefinite waiting.
4. **Testing scope:** Successful executions demonstrate the behaviour observed during testing but do not constitute a formal proof of correctness for every possible execution.
